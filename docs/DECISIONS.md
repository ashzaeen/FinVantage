## Stack

| Decision | Why |
| --- | --- |
| TypeScript for the whole backend, including the simulator | Answers the PRD's open question. One set of types shared with both clients |
| One npm-workspaces monorepo | Contracts change in one place during a 24-hour build |

## Conventions

| Decision | Why |
| --- | --- |
| Money is integer cents | Avoids float errors in a product where every figure must match exactly |
| Account balances are always positive | One rule for sums. `isLiability` gives direction |
| `LlmClient` mock always throws | Fallback paths run by default, so the app needs no key |
| Only the service worker calls the API | Host permissions apply there, and the content script stays simple |
| Ledger and document backends can be selected independently | Quarterly reports can use MongoDB Atlas while the unfinished Tiger adapter remains in memory |
| Quarterly-report PDFs live on the API server | MongoDB stores the report and artifact metadata; authenticated API routes serve the local PDF |
| Quarterly reports use the configured Gemini Flash model | One model setting is simpler for the demo; deterministic evidence and output validation remain unchanged |
| Goal pathway labels use probability-range thresholds | Low bound at least 60% is on track; otherwise a high bound at least 40% is watch; lower ranges need attention. Labels are estimates, never guarantees |
| Invalid MongoDB configuration falls back to memory only in development | A malformed local secret should not take down the whole demo; production still fails closed so persistence is never silently lost |
| Gemini calls time out after 15 seconds | Report and Copilot requests must reach their deterministic fallback instead of hanging when the provider is unavailable |
| Advisor chat retrieves only the current user's stored financial context on the server | Context stays behind the API boundary; the browser sends only conversation messages, and Gemini credentials remain server-side |
| Spending summaries, category totals, and recurring charge lists are derived from ledger transactions | Dashboard aggregates should share transaction data as their source of truth; budget limits remain explicit demo defaults until users can configure budgets |
| A quarterly report may establish a one-quarter baseline | New users should receive a useful report immediately; comparisons and largest-change analysis appear only when a prior-quarter run exists |
| Report PDFs embed Poppins and categorize goal suggestions | The artifact matches the dashboard identity while keeping maintain, review, and explore prompts visibly distinct |
| An external cron invokes the persistent API for scheduled report email | The planned Vultr API already owns Gmail credentials. MongoDB leases due schedules atomically, which survives restarts and prevents two API instances from claiming the same occurrence |
| Quarterly UI charts use report-owned monthly transaction aggregates | Recharts renders responsive bars and trends, while every displayed cent remains computed by the API from ledger transactions rather than by the browser or Gemini |
| Transactions store normalized USD cents alongside the entered currency, signed minor-unit amount, and captured historical USD rate/date | Every existing budget and spending aggregate stays comparable in USD, while the transaction list and editor preserve the user's currency and the conversion can be audited |
| Net worth history is reconstructed from the current account snapshot and recorded transaction flows | The demo has no historical account snapshots; the chart can show available ledger movement while clearly labeling that older or unrecorded activity is omitted |
| Named simulator shortcuts store only a run ID, label, and what-if settings in browser storage; the complete simulation snapshot remains in the API run history | This lets people reload and compare named plans without copying financial account data into local browser storage |
| Life-event text parsing extracts only dates, amounts, recurrence, and duration explicitly present in the user's sentence | The model may classify an event type, but it cannot invent financial assumptions; missing estimates must be supplied before a draft can be saved |
| Unsaved life-event previews compare before and after results with identical goals, what-if inputs, seed, and path count | Holding every other input constant makes the event's effect easier to understand; the draft stays unsaved until the user confirms it |

## Platform, decided 2026-11-07

These replace the Tiger Data and Vultr lines above, and the "Spacetime: enter or skip?" open question.

| Decision | Why |
| --- | --- |
| SpacetimeDB on Maincloud holds the relational data: users, income profiles, accounts, transactions, goals | Platform owner's call, after talking to the Spacetime team. Replaces Tiger Data, so the Tiger Data track is dropped |
| SpacetimeDB also handles live updates. The dashboard subscribes with the Spacetime TypeScript SDK | The Spacetime team recommended building around live subscriptions. It also fixes live updates on serverless, where the in-process SSE bus cannot reach other instances |
| MongoDB Atlas holds every document record, as the PRD says. The quarterly-agent owner writes the store | Unchanged from the PRD. Platform only adds the connection |
| The web app and the API both run on Vercel. The API is bundled into one function with esbuild | One platform, deploy on push, a preview per PR. Spacetime cannot run a server-rendered Next.js site. Replaces Vultr, so the Vultr track is dropped |
| The API reaches Spacetime over its HTTP API (SQL and reducer calls), not the WebSocket SDK | Serverless functions cannot hold a connection between requests. The browser holds the SDK connection instead |
| Spacetime subscriptions only tell the dashboard to refetch through `api`. Figures always come from the API | Keeps math first and contract validation for every number |
| `WEB_ORIGIN` is a comma-separated list, and `*` matches one subdomain label | Lets production and Vercel preview URLs call the API |
| Deploys run from GitHub Actions with the Vercel CLI, into the platform owner's Vercel account. The only repo secret is `VERCEL_TOKEN` | The repo owner is a different person, and only they can install the Vercel GitHub app or add secrets. One secret is the smallest ask |
| The Spacetime module is published from the platform owner's laptop, not CI | The schema changes rarely, and it needs no extra repo secret |
| CI is manual-only for now | It failed on Linux in the build step, the logs weren't visible without signing in, and deploys don't depend on it |
| Sign-in is our own email + password, not SpacetimeAuth. The API issues RS256 tokens and publishes its key at `/.well-known/jwks.json`. Accounts live in a private Spacetime `credential` table, with scrypt hashes | SpacetimeAuth only offers magic link, anonymous, and social logins, and the team wanted email + password. Our tokens are OpenID-shaped, so SpacetimeDB can still accept them as identities for live subscriptions |
| Bank data is modeled on Plaid: Spacetime tables mirror Plaid's objects and signs, the demo fixture is in Plaid's format, and one mapper (`packages/data/src/plaid/map.ts`) turns it into the app's `Account` and `Transaction`, which only gained optional fields | Plaid is the main bank connector. Keeping Plaid's shape at the edge means live Plaid is a data-source swap, and keeping the app types stable avoids breaking teammates' code. See `docs/DATA-MODEL.md` |
| Live updates: the browser connects to SpacetimeDB with the FinVantage sign-in token itself, and subscribes to a per-user `my_live_event` view. The module trusts only issuers listed in `trusted_issuer` | No second sign-in system. SpacetimeDB verifies the token against our published JWKS, and the view keys rows by the identity linked to the token's `sub`, so users only ever see their own events |

## Simulator and Copilot (browser agent)

Answers to the open questions above. These replace those rows.

| Decision | Why |
| --- | --- |
| **Probability range = assumption terciles.** Each path draws an assumption level that shifts its average market return and raise rate. Low end: success rate in the most pessimistic third of paths. High end: the most optimistic third | A confidence interval at 5,000 paths is about ±1%, which is false precision. This range says "if returns and raises come in below average, X%; above average, Y%", which is honest and explainable |
| Monthly steps, seeded mulberry32, fixed draws per month | Same seed means same output, and a baseline and a what-if share their randomness, so the difference is caused by the purchase alone |
| One-time purchases create a cash shortfall that monthly savings rebuild before goals get new money | A laptop is paid from cash, not from a goal. The delay shows up as goals waiting while cash recovers |
| Goals are funded "on pace" in priority order: each gets what it needs to land on its date, then leftovers speed up goals in order | Matches the PRD's joint simulation. A purchase often shows as lower odds rather than a later date, so cards can lead with either |
| **A rental replaces current housing.** The simulator applies rent minus the current mortgage payment | The demo profile owns a condo and goes apartment hunting. Adding rent on top of a mortgage makes every goal impossible and is not what a mover does |
| **Safe rent** = current housing payment + monthly savings not needed by non-negotiable goals, rounded down to $50 | Ties the threshold to the user's must-hit goals, which is what the card says it protects |
| **Vehicle**: assume 60 months at 7% APR, whole-dollar payment, total cost includes interest | The privacy rule limits the payload to price, so terms are assumed and named on the card ("at an assumed 7% over 60 months") |
| **Checkout Smart Move**: pay from checking down to the buffer target, put the rest on the 0% promo card, pay off in equal whole-dollar amounts before the promo ends | The PRD's example card. No plan when checking covers it or no usable promo card exists |
| **The headline is chosen in code** (`pickHeadline` in math-core): one month of delay scores like a 10-point drop in odds; tiny changes are ignored; a goal that becomes unreachable wins; a goal that was already unreachable only leads when nothing else moved | Keeps "math first": the model words the headline but never picks it. The LLM card is rejected if it does not name the headline goal |
| `GoalImpact` gains `probabilityLowAfter` and `probabilityHighAfter`; `CopilotMetrics` gains `currentHousingCents`, `monthlyChangeCents`, `vehicle`, `splitPlan`, `headline` | Additive. Cards say "from 93–94% to 76%", which needs the after values |
| Demo profile gains a "Japan trip" goal (priority 2, $4,500 by June 2027) | Gives the checkout demo a concrete, relatable goal to lead with |
| The Life Simulator's supplied sample planner uses a separate deterministic contribution schedule and labels its figures as samples | The page's expected date outputs come from simple month-by-month funding rules; this keeps those scenario illustrations distinct from account-linked Monte Carlo projections |
| Extension rejects dollar prices tagged with another currency ("$1,499 CAD", "CA$1,499") | PRD: skip non-USD and never guess |

## Good-move cards

| Decision | Why |
| --- | --- |
| Every card has a **verdict**, chosen in code: `caution` (hurts a goal or the cash cushion), `good` (fits the plan or beats the alternatives), `neutral` | The Copilot advises in both directions. The model words the stance but never picks it. The overlay colors the card by verdict (red, green, blue) |
| New page type `debt_payment` (item `credit_card_payment`) | Paying off debt is the clearest good move. The payload stays price, item type, and merchant only |
| A card payment is matched to the **highest-rate card with a balance**, paid from checking | The page cannot send which card (privacy rule), and the highest-rate card is the one a payment helps most |
| Interest saved = amount paid × the card's rate, for a year, in whole dollars. Paying in full frees the minimum payment, which the simulator returns to savings each month | Honest, explainable figures. A partial payment frees only the interest |
| **Alternatives** rank where a dollar earns the most: each debt at its rate, investing at the assumed 7%, the best savings account at its rate | Lets a card say why a choice beats the others ("a 23% guaranteed return, better than investing or savings") |
| An affordable checkout (no goal hit, cushion intact) is `good`: the card affirms it and steers payment away from high-rate card debt | Reinforces good habits instead of staying silent |
| Headline gains a `gain` kind (a goal gets sooner or more likely), used only when nothing got worse | Positive changes deserve a mention, but a loss always outranks a gain |
| `CopilotCard` gains `lead`, the one figure shown large and on the badge | Works for both directions: a goal's odds, interest saved, or "on track" |
| Goal likelihood is shown as **plain status words**, chosen in code (`GOAL_STATUS` in math-core): on track (90%+), likely (80-90%), at risk (50-80%), unlikely (10-50%), out of reach (under 10%). Cards never say "odds". The percentage range stays in a small "Chance" row near the disclaimer | "Odds" read like gambling. Words land faster for a bank audience, and keeping the range on the card honors rule 7 |

## Demo store

| Decision | Why |
| --- | --- |
| The demo runs on a believable store (Circuit & Co.: 12 products from $15 to $3,299) plus the rental, car, and bank sites, opened from a plain browser start page with no scenario hints | Judges see the Copilot reach different verdicts live from the same data, instead of a scripted outcome per page |
| The Copilot appears on product pages (when you look at an item) and again at checkout | Advice at the moment of decision. Both pages send only the price |
| On localhost, dismiss and snooze are keyed by path and query, so each product counts separately | Products share one page and differ only by `?id=` |
| When a purchase makes a goal unlikely or out of reach, the Smart Move points to a cheaper option or waiting, never to financing | A split payment protects the cash cushion, not the goal. Suggesting financing there would be bad advice |
| The demo server also serves `.js` files from `mock-pages/` | The store's catalog lives in one shared script (`store.js`) |
| The Copilot **re-evaluates when the page's price changes** (a MutationObserver, debounced 600 ms; it still reads only the rule's price element). An open card updates in place; a price that disappears removes the card; stale replies are dropped | Picking a different payment amount or quantity should change the advice live. That is the "actively guiding" moment of the demo |
| A card payment of no more than the minimum is `neutral`: the card shows the interest still charged on the rest and, when checking can cover the full balance above the cushion, suggests paying it all. A partial payment above the minimum stays `good` but makes the same suggestion | Calling a minimum payment a "great move" would be bad advice |
| `GeminiClient` uses the REST API through `fetch`, not the SDK | No new dependency, and every request and failure is visible in one file. Structured output sends `responseMimeType: application/json` with the schema's types upper-cased |
| Copilot cards wait at most 2 seconds for Gemini, then show the template card | The PRD requires a card within 3 seconds |
| Copilot cards ask Gemini for `thinking: "minimal"` (`LlmRequest.thinking`, sent as `thinkingConfig.thinkingLevel`). Other calls keep the model default | Tested live on 2026-11-07: with default thinking, `gemini-3-flash-preview` took over 15 s on the card prompt, so every card fell back. With minimal thinking it answers in about 1.1 s and passes the guardrail. The figures are fixed, so there is nothing to reason out |
| The demo key uses `gemini-3-flash-preview` for both tiers | It is an AI Studio free-tier key (5 requests a minute per model). 3.5-flash was close to that limit and slower. 3.6, 3.7, and 3.8 flash returned 503s or hung, and 2.5-flash is closed to new users |
| An accepted Gemini card is cached in memory, per client, keyed by the exact prompt (up to 200 cards). Failed or rejected cards are never cached | The simulator is deterministic, so the same page gives the same prompt. Reopening a page or replaying the demo reuses the card instead of spending one of the free tier's 5 requests a minute. The cache resets on restart |
| A card that falls back to the template logs one line with the reason. The mock provider is not logged | A silent fallback hid the timeout when Gemini was first tested. The mock always throws by design, so logging it would be noise |
| Demo-site submit buttons (place order, schedule payment, credit application) say "Demo site: nothing was sent" instead of doing nothing | No dead buttons during judging, and nothing pretends to be a real transaction |
| `COPILOT_GEMINI_MERCHANTS` lists the merchants whose Copilot card Gemini writes (case-insensitive). Unlisted merchants get the template card with no model call. Unset means every merchant uses Gemini | The free key allows 5 requests a minute and 20 a day. Spending it on the mock demo pages left none for the live-site moment. Set to `Amazon` for the demo |
| A site rule may list several price selectors, tried in order; the first element with a clean USD price wins | Amazon's layout varies by product and by test group. The main selector (`#corePriceDisplay_desktop_feature_div .priceToPay`) matched every product checked; the fallbacks cover layouts without it |
| Amazon is `checkout` / `retail_purchase`, merchant "Amazon", product pages only | Cart and checkout need a signed-in account to check, and a product page already shows the advice at the moment of decision |
| Closing a card (dismiss) hides it on that page only; "Snooze this site" covers the whole host. On localhost both are per page | Keyed by host alone, closing one Amazon product's card hid the Copilot on every product. The page key (host and path; plus the query on localhost) stays in `chrome.storage.session` and never reaches the API |
| The Copilot card is written for an everyday shopper: a verdict with an icon and a word (Heads up, Looks good, Worth a look), one plain sentence, the goal, "Why", "What you could do", then the numbers with plain labels. 15 px body text, nothing under 12 px | A teammate flagged the card as hard to read. Color alone carried the verdict, and labels like "Fixed costs of income" and "Cushion target" were jargon |
| A "caution" card is a red **Warning** when a goal ends at risk, unlikely, or out of reach, or the purchase is more than checking holds; otherwise an amber **Heads up** (goal still likely, a short delay, a dip under the cushion). Chosen in `toneFor` in the overlay from math-core fields | One amber level undersold serious cards: a desktop that took the Japan trip from 93% to 54% looked like a nudge. The amber token is new; the red matches the dashboard's `--critical` |
| The card rewords math-core status words: "likely" shows as "probably OK", and a change reads "At risk (was on track)". Math-core and the dashboard keep their words | "On track → Likely" read as good news on a warning card |
| One term for the cash reserve: "safety cushion". Not "emergency fund", which is also the name of a demo goal | The card used "cushion", "buffer", and "cushion target" for the same thing |
| A Gemini card is rejected, and the template shown, if it uses finance jargon (`CARD_JARGON`) or a negative dollar amount | Plain words are now a rule the code enforces, like the number check |
| The safety cushion figure is offered to Gemini only when checking-after is computed, and the payment-split figures only when the template would offer the split | Given the cushion on a rental, Gemini claimed the rent drops it below $2,500, which the math never said. Given the split on a goal that fell out of reach, it suggested financing, which the card must not do. Withholding the figures means the number check rejects those claims |
| A purchase larger than checking reads "$299 short", never "-$299" | Seen live on a $3,699 laptop |
| Gemini writes cards on every site again (`COPILOT_GEMINI_MERCHANTS` unset) | The paid key removed the quota limit. The template backup is unchanged |
| A purchase or card payment spends spare checking (checking above the safety cushion) first; only the rest enters the simulator as cash that must be rebuilt from savings before goals get money (`spareChecking`, `purchaseForSimulator`) | Before, every purchase came fully out of goal savings, so someone with $14,000 idle in checking was told a $1,499 laptop delays their goal. On the demo profile the Arc 14 laptop is now an amber heads-up (it dips under the cushion) and the Arc 16 Pro is the red warning |
| Checking means the bank's available balance when it reports one | Plaid's available balance excludes pending charges; "can I pay for this now" is about what's spendable |
| The 0% split is offered only when the amount fits the promo card's remaining credit (when the bank reports it) and the monthly payment fits within monthly savings | Before, it could suggest putting $2,799 on a card with $500 of credit left, or a payment the user can't make |
| "No financing" and the red Warning trigger only when this purchase moves a goal into unlikely or out of reach (or at risk, for red), not when the goal was already there | The demo's House down payment is already "unlikely"; a laptop that slips it 2 weeks wrongly lost the split and turned red |
| A card payment bigger than checking reads "$X short", like a purchase | The same negative-balance problem, on the debt page |
| Once a signed-up user links a bank, the linked bank replaces their demo copy's accounts and those accounts' transactions (`preferLinkedBanks`, applied in `createStores`). Goals, income, life events, and hand-added accounts stay. Unlinking every bank brings the demo copy back | Linking added the bank on top of the demo copy, so a user had two checking accounts and the Copilot, simulator, and net worth counted cash twice. The team treats Plaid Sandbox values as the user's real money for the demo. Both ledgers mark the demo copy with `<userId>__` IDs, so one wrapper covers both. Changed `apps/api/src/bank.test.ts` to match. Confirmed by the platform owner 2026-11-08 |
| Quarterly reports follow the same rule: `dataSource` is `bank` once a bank is linked. Bank reports take the quarter's income, spending and savings from transactions, skip simulation runs made on the demo copy, and, when the quarter has no run, use the newest one or run one now (`outlookAsOf`). Simulations for a linked user take income, spending and savings from the last three months of transactions | A linked user's report added the demo copy's figures and goal ranges to their bank's, and a user who had never loaded the demo got a 409 because only `load-demo` saved runs. The Copilot still reads the profile's figures, because its fixed-cost checks pair with them; switching it is the Copilot owner's call |
| The extension follows the dashboard's sign-in: it reads the `fv_token` cookie (`SESSION_COOKIE` in contracts) from the web app's origin through `chrome.cookies`. Signed in there, cards use that user's accounts and linked banks; signed out or expired, the shared demo profile. The popup shows who is signed in, opens the dashboard's login, and signs out of both | The extension always used the shared demo token, and the demo user can't link a bank, so the Copilot never saw Plaid data. A separate popup sign-in worked but meant signing in twice and could disagree with the dashboard. The cookie permission is scoped to the web app's origin; the extension never sees a password. The token helpers moved to contracts so the web app and extension share them |
| A credit card's rate is its purchase APR. Plaid's "special" (promo) APR replaces it only when the user has entered the promo's end date | Plaid Sandbox's card has a 0% special APR on $1,000 next to a 12.5% purchase APR. Taking the special rate showed the card as 0%, so the Copilot never warned about card interest and found no card worth paying down. The demo's 0% Promo Card has an end date, so it stays 0% |
| Spare cash is checking above the cushion plus savings no goal is using (spendable savings minus goals' saved amounts; an HSA and CDs don't count). When checking can't cover a purchase or card payment but spare savings can, the card says to move that amount from the largest savings account first, and that shortfall alone is not a warning. Savings beat the 0% split | A Plaid Sandbox person with $100 in checking and $55,000 in savings was told they were "$1,399 short" for a laptop. The demo profile's goals use all its savings, so its cards don't change. `computeCopilotMetrics`, `purchaseForSimulator`, and `splitPlan` now require the goals, so leaving them out is a type error rather than overstated spare cash |
| A purchase or card payment is judged on what it changes. The cushion counts only when checking was at or above it beforehand: then dropping below it warns, and a transfer restores it. When checking was already under the cushion, a payment checking covers is fine, the card leaves the cushion out, and a transfer covers only a shortfall | A $12.99 extension cord told a Plaid Sandbox user (checking $100, cushion $2,500) to "move $2,413" and to keep a cushion they were already under. Leaving the cushion figures out also stops a model from bringing it up, through the number check |
| The extension installs from the dashboard's Copilot tab: a zip, loaded with Developer mode's "Load unpacked". The web build (`apps/web/scripts/bundle-extension.mjs`) builds it from the current code and points it at that dashboard's API and origin (`NEXT_PUBLIC_API_URL`, `VERCEL_PROJECT_PRODUCTION_URL`, or `EXTENSION_*` overrides). `apps/extension` changes now redeploy the web app | Teammates and judges had no way to install it without the repo. The Chrome Web Store is the only one-click install and its review is too slow for the hackathon |
| The Life Simulator sends event assumptions only; the API rebuilds goals, monthly savings, and the as-of date from the same server snapshot used across the dashboard before calculating. If individual target dates imply contributions above monthly savings, the baseline allocations are proportionally scaled to fit available cash. Exported PDFs recalculate from that same source and include the event assumptions, goal funding comparison, timeline, and contribution changes. The extension overlay uses the dashboard's purple, white, and semantic green/amber/red palette | A browser could submit stale or edited goal balances, making the Overview, simulator, and exported comparison disagree. The baseline chart also showed individual goal targets whose combined monthly contributions exceeded actual savings |
| Life-event insights compare each event projection with the goal's current saved/target amount and baseline funding date. Per-goal High means an event makes a previously fundable goal unfunded or delays it by at least six months and at least 75% of its remaining baseline timeline. Overall High requires that at least half of included goals meet that threshold, or the event uses all monthly free cash. Moderate delays and timing conflicts are Medium; unchanged dates with cash remaining are Low. Show a colored status per goal so one severe goal does not color the entire comparison red | A flat one-year delay rule made long-term goals turn every event red, even when the change was modest relative to their current timeline |

## Spending categories, decided 2026-11-08

## Advisor, decided 2026-11-08

| Decision | Why |
| --- | --- |
| The Advisor retrieves with a brief plus tools, not embeddings. Each turn gets a compact brief computed in code (net worth, income, budgets at risk, bills, goals and their odds, life events, the latest report, recent Copilot scans), and Gemini function calling reaches everything else through about 15 typed tools (`apps/api/src/advisor/tools.ts`) | Financial records are structured, so filters answer "what did I spend at Amazon in October" exactly where similarity search would guess. Tools also let the Advisor run what-ifs, which retrieval cannot |
| Advisor tools read through the app's own GET routes, called in process as the signed-in user (`advisorReadApi`). The handler passes the request's Authorization header through `HandlerContext.authorization` | The Advisor sees exactly what each page shows, from the same code, contract-checked. Only GET routes are listed, so a tool cannot change data |
| Records go to the model with every `...Cents` field turned into a dollar string (`forModel`) | The model never converts or calculates money, which is where invented figures come from |
| Chat answers pass a number check: every number must appear in the brief, a tool result, or the conversation (`validateGrounded`). Counts up to 12 are allowed. A failure gets one retry that names the bad numbers, then the safe answer, written in code from the brief and tool summaries (`source: "fallback"`, shown as "Safe Answer") | Rule 1 applies to chat as much as to cards. The safe answer means the Advisor never shows an empty state when Gemini is down |
| Chat answers are capped at 250 words, not the card's 60 | A conversation needs room; cards keep their cap |
| `draft_life_event` returns a draft attachment and never saves. The amount must be one the user typed; otherwise the tool tells the model to ask. The user saves with "Confirm and Save", which calls the existing `POST /v1/life-events` | Rule 9, and the model must not invent the dollar impact of a life event |
| `check_purchase` runs the Copilot pipeline (simulator, then math core, then the template card) without saving a Copilot event | Asking "can I afford it" in chat should not fill the Copilot feed |
| Conversations are saved (`advisor_conversations`, `advisor_messages` in MongoDB; memory otherwise). The last 20 messages are replayed to the model | Agent memory in Atlas, as the PRD plans. Earlier answers already passed the number check, so their figures may be repeated |
| `LlmClient.chat` is optional. Fakes and older callers that only have `generate` still work; the Advisor treats a client without `chat` as unavailable | Additive change to the one wrapper |
| Advisor routes moved from `routes/agents.ts` to `routes/advisor.ts` | Reports and the Advisor have different owners |
| New figures in advice come from code, not the model. `plan_goal` (gap, months left, monthly need), `find_savings` (3-month averages of "wants" categories, cuts capped at half a category, then a what-if), and `calculate` all compute in math-core (`packages/math-core/src/advisor.ts`). Their results enter the number check like any tool result, and each attaches its working, shown as "How These Numbers Were Worked Out" | Useful advice needs numbers that appear nowhere yet ("cut restaurants by $Y"). The rule is that the model never does arithmetic, not that it never states a new number |
| `calculate` evaluates + - * / % and parentheses with a hand-written parser (no `eval`). Every number in the expression must already be grounded: in the brief, a tool result, or the user's words. 12 and 100 are always allowed | The model picks the formula, but cannot slip in a figure of its own, and the working is shown to the user |
| `web_search` runs Google Search grounding in a separate Gemini call (`LlmClient.webSearch`), never combined with the function tools in one request. Only the query is sent. Code refuses a query that names the user or their email, contains a dollar amount, or contains one of the user's own figures (`privacyProblem`). Account names are allowed, since they are bank product names such as "PNC Checking" | Questions such as "should I get this card?" need a product's current published terms. The query leaves our server, so it must carry nothing that identifies the user or their money |
| Figures from the web are allowed in answers once a search returns them, and the answer must say they come from the web and may change. Sources are shown under "From the Web" | They are the publisher's figures, not FinVantage's computation, so they are labeled as such |
| The Advisor aims to answer any money question, so it gets general building blocks, not one tool per question type: `simulate_scenario` (any mix of one-time and monthly changes, a loan, a savings change, a new goal, a moved goal date), `finance_calc` (loan, growth range, payoff, save-for, time-to), `calculate`, `web_search`, every read tool, and drafts. The prompt tells the model to understand the decision, gather facts, compute with tools, and answer with options | Versatility. A new kind of question should need a better prompt, not new code |
| `simulate_scenario` maps changes onto simulator inputs (`applyScenario` in math-core): one-time and monthly changes become unsaved life events, a loan becomes its down payment plus its payments over the term, and goals are added or moved. The simulator is unchanged; it only reads an event's date, amount, recurrence, duration, and linked goal | Any decision runs through the same engine as the dashboard, with no new engine code to maintain |
| Every amount, rate, and term a scenario or formula tool takes must already be grounded (the user's words, their data, a search, or the brief's named assumptions). The brief lists the assumptions: a 60-month loan term and 4%, 7%, and 10% growth returns | The model picks the inputs but cannot invent one. A default it uses is a named constant it must say it assumed |
| Growth is always a range across three named returns, never one projected number. Investing and tax questions get explanations of how each option works, not instructions | PRD rule 7 and the "no tax advice" non-goal |
| `draft_goal` proposes a goal, with its own odds and its effect on other goals, and never saves. The user saves with "Confirm and Save", which calls `POST /v1/goals` | Rule 9, the same as life-event drafts |
| The number check lets dates and years near today through (5 years back to 50 ahead): ISO dates, "March 15", and standalone years. A number after "$" or inside a longer number is never read as a year | "Book by March 15, 2027" is a date, not a computed figure, and was being rejected |
| `npm run eval:advisor` runs a bank of about 40 varied questions against real Gemini, with in-memory stores and the demo profile, and reports which were answered, which got the safe answer, and why | The measure of versatility. Tune the prompt and tools against it |
| Advisor answers can carry interactive visuals (attachment kind `visual`): a loan explorer, a goal planner, a growth comparison, and a card evaluator. Tools attach them: a loan in `simulate_scenario` or `finance_calc`, a new goal or `draft_goal`, a growth formula, and the new `evaluate_card`. At most one visual of each kind per answer | Results for decisions read better as something to explore than as prose. The tools already hold the figures |
| A visual recomputes through `POST /v1/advisory/visuals` (`apps/api/src/advisor/visuals.ts`) when the user moves a slider or flips a chip. The tools build the first view with the same functions. The browser does no financial math; slider values are the user's own choices | The math-first rule, and the web app's rule against computing figures, hold for interactive widgets too |
| The visuals use the landing page's Try a Purchase style: a floating card, pill chips, a hero figure, a before/after strip between hairlines, and one-hue fan charts (`--fan-*`) with a crosshair and a caption below. Status colors appear only on verdicts, with an icon and a label. Every chart has a table view | One family of visuals that matches the product's best-looking chart |
| The goal planner defaults to funding the new goal first, with a chip to fund it after the user's other goals. Saving with "Fund It First" puts it at priority 1 and moves the user's other goals down one | Funded last, a near-term trip usually gets nothing (the other goals take every dollar), which shows 0% and helps nobody. Making the choice visible shows the real trade-off |
| Spending averages use the last three full months, or this month so far when those months have no spending (`spendingMonths`), and the visuals and tools say which. The card evaluator sizes spending from the user's cards, or from their everyday needs and wants spending when the cards show no purchases | New and sparse accounts would otherwise show $0 everywhere |
| Growth rates are not fixed. `finance_calc` growth and the growth visual take up to four rates, each labeled with its source: `user` (the user said it, or set it in the visual), `web` (a web search found it, such as an index's long-run average, with its sources linked), or `assumed`. The 4%, 7%, and 10% band is only a fallback when neither exists, and is labeled assumed. This replaces the earlier fixed band | Users compare real things ("the Nasdaq or the S&P 500?") and have their own expectations. A fixed 7% answered neither |
| Numbers inside well-known financial names (S&P 500, Nasdaq-100, Russell 2000, Dow 30, 401(k), 529 plans) are names, not figures, in both the answer check and the web search privacy check (`withoutFinancialNames`) | "S&P 500" was refused as a search query because the user had $500, and read as an invented figure in answers |
| Comparison lines use `--series-1` to `--series-4`, a fixed-order palette checked for lightness, chroma, colorblind separation, and contrast on white | Up to four rates need distinct, accessible colors; each also has a legend row and a source badge, so color is never the only cue |
| **Rule 1, narrowed for chat (decided 2026-11-08 by the Advisor owner):** the chat answer check covers dollar amounts only. Every dollar amount ("$570", "$9.1k", "$1.2 million", "570 dollars") must match a figure the model was given, within 3% or a dollar for rounding. Plain numbers and percentages are not checked. A `...Cents` field grounds only its dollar forms. Tool inputs (`calculate`, `simulate_scenario`, `finance_calc`, `draft_goal`, `evaluate_card`) stay exact through `isGroundedNumber`. Copilot cards keep their full check (rule 2). This replaces the earlier all-numbers chat check and its date and year exceptions | The all-numbers check blocked general advice ("under 30% utilization", "7 years on your report"), rounding ("about $570"), and counts, while the risk the PRD cares about is a wrong figure about the user's money. Money stays protected; everything else reads naturally |
| When a retried answer still has an unchecked amount, the reply is that answer without the sentences holding the amount, with a note that one was left out (`withoutSentences`), as long as at least 12 words remain. Otherwise it is the safe answer written in code | The old fallback, a summary of the user's finances, didn't answer general questions such as "how do I raise my credit score?" |
| `check_purchase` no longer takes vehicles. A financed car (or any loan with an APR) goes through `simulate_scenario` with a loan, which uses the user's own price, down payment, APR, and term. A safe answer shows what the tools found and leaves out the general brief once any tool returned something; a retry tells the model to call a tool for a missing figure | Live, "a $10,000 car at 7.49% with $3,000 down" used the Copilot's assumed 7% and 60 months with no down payment, then failed the money check twice, and the safe answer padded itself with net worth and budgets |

|---|---|

## Subscriptions, decided 2026-11-19

| Decision | Why |
|---|---|
| Subscriptions are a view over recurring charges, split into **Subscriptions** (wants and uncategorized) and **Bills** (needs, loan and card payments), with the user able to move one across. Saving, investing and income are in neither. No new category | Extends the 2026-11-08 decision that subscriptions are not a category. Streaming and gyms sit in different categories, and a mortgage is not something to cancel |
| FinVantage records what a user says about a subscription (keep, cancelling, cancelled) and checks whether a cancelled charge stopped. It never cancels, negotiates or pays, and takes no fee, unlike Rocket Money's concierge. The UI says so at the point of confirming | Rule 4, suggest only. Recording a choice moves no money; the next charges show whether it held |
| Choices are stored apart from the Plaid-shaped bank tables, in a `SubscriptionStore` with a snapshot of the charge. Memory by default, and MongoDB (`subscription_states`, one document per user and subscription id) when `DOCUMENT_BACKEND=mongodb`, picked in `createStores` with the same fail-closed rule as the other document stores. **Written but not yet run against a live Atlas cluster, and the platform owner has not agreed the store-set change** | A cancelled subscription's stream ends at the bank, so without the snapshot it would vanish from the list with its savings. User choices are not bank data, so they do not belong in `recurring_stream` |
| A subscription costs its latest charge; a bill keeps the bank's usual amount | The bank's average sits between the old and new price after a rise. Bills vary, so their average is the better guide |
| A cancelled subscription whose charges continue past one billing cycle (up to 35 days) is flagged Still Charging, stays in the monthly total because it still costs money, and is credited no savings until the charges stop | The total should say what a person is really paying, and a saving that has not happened should not be shown |
| A subscription is flagged only from what its own charges show: a price rise (within 120 days), a possible duplicate from a short fixed list, a recent start (only if the ledger reaches back far enough), a yearly charge due within 30 days, and a cancelled one that charged again. No "unused" claim and no "you overpay" claim | There is no usage data and no price benchmark, and inventing either would break the math-first rule |
| The demo is at exactly 500 transactions, the most the Transactions page loads, so its subscriptions are 6 rather than about 10: new ones are short-lived or a stream with no ledger charge | A monthly subscription costs 11 transactions. Raising the limit needs pagination, which is its own change |
| "Put This Toward a Goal" records a cancelled subscription's monthly cost as a positive, recurring, open-ended `custom` life event linked to the chosen goal, through the existing preview and create routes, and only after the person previews it and presses Confirm. It does not use the life-scenario path | A scenario's cost cannot be negative, so a saving does not fit it without changing another workstream's math. The panel finds a matching event later so it is never added twice and can be removed; no other page lists or removes plain life events. It can double count if the bank has already stopped the charge and balances have grown, and the panel says so |
| The quarterly PDF gets a Subscriptions card on the evidence page, built from the same `visuals.subscriptions` figures as the Reports page, and left out when they are null | No figure is recomputed for the PDF |
| The price flag carries the latest charge (`currentCents`, additive and nullable), and the page sentence, the Ask for a Lower Bill draft and the Advisor tool use it | A bill shows the bank's usual amount, so "was $82.85, now $101.31" paired a charge with an average. Found by looking at the demo data after moving it to 2026-12-03 |
| The demo profile is generated as of the presentation date, 2026-12-03, not as of the day it is built | The app reads the real clock, so data that ends on the day of the demo shows only upcoming dates. Until then the ledger holds charges dated after today |
| A new dashboard route must be added to the route list in `apps/web/src/proxy.ts`, or a visitor who opens it directly gets the read-only demo token and every write fails | Found when the Subscriptions page could not save: it was missing from the matcher |
| A drafted message is written from a template first. The model's wording is used only if every number in it is one of the user's own figures, it is at most 120 words, and it has no link or address, no threat (a lawyer, a chargeback), and no claim that a price is unfair or that others charge less. Otherwise the template is used. It is generated when asked for, never on page load, and nothing is sent | A message is longer than a 60-word card, so it gets its own cap. ## Dashboard enhancements, phase 2, decided 2026-11-23

Phase 2 adds the planning figures. Each is worked out in `packages/math-core/src/planning.ts`, served by `apps/api/src/routes/planning.ts`, and only worded and drawn by the web app.

- **Target allocation lives on the spending profile document** (`SpendingProfile.targetAllocation`, optional), not on `User`. `User.preferences` is a SpacetimeDB column, so changing it means republishing the module. The profile document takes an optional field freely.
- **`PATCH /v1/investments/targets`, not PUT.** It changes one part of the profile. Targets must add to 100% or the API returns a 400. The page previews a preset and saves only on Save Targets (rule 9).
- **The mocked score estimate is a documented rule** (`UTILIZATION_SCORE_POINTS` in `planning.ts`): always a range of plus or minus 15 around a point estimate, always `mocked: true`, shown beside `MockedBadge`. The what-if changes nothing, and `POST /v1/credit/what-if` is on the demo token's allowlist because it saves nothing.
- **Debt payoff leaves the mortgage out.** It covers cards and loans. A debt with no stated minimum is assumed to need 2% of its balance, at least $25. A 0% promo card is treated as 0% for the whole plan.
- **Goal funding ignores growth and interest.** Needed per month is the remaining amount over months left, rounded up. The simulator's odds also count growth, so the two can disagree, and the Goals page says so. There is no "shortfall" verdict.
- **`spendingContext(deps)`** in `routes/spending.ts` is the shared source for the spending profile, catalog, transactions, six-month summary and budgets.
- **Budget suggestions save nothing.** Each row has an Add This Limit button that calls `setBudget`.

## Dashboard enhancements, phase 3 (second group), decided 2026-11-23

Simulator forecasts and the chat and edit tools: LE3, LE4, IV5, TX5, AD4 and AD5. Not started: GO2 and GO4 (goals math).

- **Forecasts live in the simulator, beside `simulate`, and change nothing in it.** `forecastCash` returns free cash for 24 months as a 10th to 90th percentile band. It is the same monthly pool the goal run draws from, before any of it goes to a goal, and it consumes random draws in the same order, so the same seed gives matching months. `projectRetirement` grows a balance at the invested return and volatility with a yearly fan. Both are seeded and pure. Tests are in `packages/simulator/src/index.test.ts`.
- **The stress test needs no new simulator input.** `POST /v1/life-events/stress` turns the two switches into a change in monthly savings (`stressMonthlyChange` in `math-core`: `-(income x drop + usual rent x rise)`) and passes it as the existing `whatIf.monthlySavingsDeltaCents`. Usual rent is housing spending over the last three full months. It runs at a fixed seed and 2,000 paths, so the same switches give the same answer, and it saves nothing. Switches are capped at 50%.
- **The retirement fan (IV5)** is `POST /v1/investments/retirement`, always `mocked: true`. It starts from the user's `ira` accounts, adds a fixed monthly contribution, and ignores taxes and inflation, which the card says. The page takes ages and a contribution; only the number of years is sent. Both new POSTs are in `COMPUTE_ROUTES` and on the demo token's allowlist because they change nothing.
- **Bulk edit and split (TX5)** are two routes: `POST /v1/transactions/bulk-category` (up to 200 ids, every id and the category are checked before any row changes) and `POST /v1/transactions/:id/split` (two to five parts that must add up to the original, same sign, US dollars only). A split updates the original row with the first part and adds new rows for the rest, so no store gained a delete method. The ledger total never changes. The page has a Select mode and a bar that moves the selected rows on a confirm press.
- **Two scenarios in chat (AD4)** is a wrapper on each Advisor visual: Compare Two Scenarios starts B as a copy of what is on screen, each side recomputes through the existing `POST /v1/advisory/visuals`, and a table shows B minus A on headline figures chosen in `lib/visualCompare.ts`. No new API.
- **Tap a number (AD5)** makes a figure in an answer a button only when a calculation attachment's result contains it (`lib/figureLinks.ts`). The drawer shows the figure, what it is, the working with its inputs, the answer's date and the sources the answer cited. A figure with no calculation behind it stays plain text. Not every figure carries a working yet, so some stay untappable until the Advisor's tools attach more calculations.

## Dashboard enhancements, phase 3 (goals math), decided 2026-11-23

GO2 and GO4. With these, every phase 3 idea is built except Delete My Data (ST2), which waits on a decision.

- **The priority model is the simulator's first step.** `goalAllocation` (`packages/math-core/src/planning.ts`) hands the monthly savings to goals in priority order, each getting what it needs per month to land on its date (from `goalFunding`) until the money runs out. What is left over is shown as Not Assigned. A goal marked achieved needs nothing. `GET /v1/goals/allocation`. It ignores growth and interest, so the simulated odds can differ, and the card says so.
- **A rebalance is a new priority order, not a transfer.** The Goals tab has no per-goal contribution, so the only lever is rank. A reorder is suggested only when a **fixed-date** goal is short, a **flexible** goal ranked above it is fully funded, and ranking the fixed goal just above that goal makes it whole. The suggestion states the dollars a month moved and each affected goal's new monthly amount and months later than its date (or "paused" at $0). It never suggests moving one flexible goal behind another, which would only swap which of them is late.
- **Apply This Plan previews, then saves only on Confirm** (rule 9). It updates the priority rank of the goals whose rank changes through the existing `updateGoal` route. No money moves. On the demo data the one short goal is flexible, so no reorder is offered; marking it fixed-date shows the suggestion.
- **New chart piece:** `StackedBar` in `components/charts` (one bar split into parts with a legend that doubles as the text version).
